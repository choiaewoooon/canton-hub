3가지 접근 방식 — 어떻게 만들까?

동일한 기능셋을 어떤 전략으로 구현할지 비교합니다. 추천: Approach B

A

풀 빌드 — 처음부터 완성형

3개 페이지(Dashboard + Analytics + Feed)를 한 번에 개발

구현 범위:
• Dashboard: KPI 6개 + 가격차트(캔들) + B/M Ratio + 최신뉴스 3개
• Analytics: 시계열 차트 7종 + 밸리데이터/앱 리더보드 + 보상구조
• Feed: 트위터 피드 + 뉴스 + 캘린더 + 생태계 접근 가이드
• FastAPI 백엔드 + WebSocket 실시간 업데이트

장점: 완성도 높은 상태로 바로 런칭
단점: 개발 기간 길고 복잡도 높음. 런칭 전 피드백 불가
예상 규모: 큰 프로젝트
B

점진적 빌드 — Dashboard 먼저, 나머지는 Phase 2 ⭐ 추천

핵심 Dashboard를 먼저 완성하고, Analytics/Feed는 이후 추가

Phase 1 (먼저 런칭):
• Dashboard 페이지 1개 — KPI 카드 + CC 가격차트 + B/M Ratio 차트 + 최신 트윗 요약
• FastAPI 백엔드 — 기존 collectors 재활용 + 계층형 캐싱
• 실시간 가격 업데이트 (WebSocket or SSE)
• 다크 테마 + Tremor 컴포넌트

Phase 2 (이후 추가):
• Analytics 탭 — 상세 차트 + 리더보드
• Feed 탭 — 뉴스/캘린더/생태계 가이드

장점: 빠르게 런칭 → 피드백 → 개선. 기존 봇과 홈페이지 병행 가능
단점: 초기에는 기능이 제한적
예상 규모: Phase 1은 중간, 전체는 큰 프로젝트
C

MVP 최소 — 기존 봇 데이터를 웹으로만

현재 텔레그램 봇이 생성하는 이미지 카드 + 텍스트를 웹에 그대로 표시

구현 범위:
• 단일 페이지 — 현재 봇의 일일 카드 이미지 + 텍스트 리포트 표시
• CoinGecko 위젯 임베드로 실시간 가격
• 기존 bot.py에서 데이터를 JSON으로 저장 → 정적 사이트로 제공

장점: 매우 빠른 구현, 기존 코드 거의 그대로 사용
단점: 홈페이지라기보다 "봇 리포트 웹 뷰어"에 가까움. 차별화 부족
예상 규모: 작은 프로젝트
